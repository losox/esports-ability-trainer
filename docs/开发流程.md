# 开发流程

> 当进入开发阶段（初始化项目、写功能、提交代码、测试、部署）时，必须阅读本文档并遵从。

---

## 一、Git 分支策略

```
main      ← 生产分支，受保护，只接受PR合并，每次合并触发Vercel自动部署
├─ dev    ← 开发分支，日常开发在此
├─ feature/d1-reaction       ← 功能分支，命名格式：feature/维度名-功能描述
├─ feature/homepage           ← 如：feature/homepage
├─ fix/training-hud           ← 修复分支：fix/问题描述
└─ refactor/module-structure  ← 重构分支：refactor/重构描述
```

**规则：**
- 不直接往 `main` 提交
- 功能分支从 `dev` 拉出，完成后 PR 合回 `dev`
- `dev` 测试通过后 PR 合并到 `main` → 自动部署
- 分支命名用英文小写+连字符

---

## 二、提交信息规范（Conventional Commits）

```
<type>(<scope>): <subject>

type:    feat | fix | refactor | test | docs | chore | style | perf
scope:   模块名（如 d1-reaction, homepage, auth, supabase）
subject: 简短描述（中文，一行）

示例：
feat(d2-aim): 实现瞄准精度训练3D场景
fix(d7-flex): 修复棋盘切换计时不准确
refactor(shared): 抽取SceneBase为所有模块基类
test(d1-reaction): 添加反应速度计分单元测试
docs: 更新产品规划文档至v4.0
chore: 配置ESLint和Prettier
```

## 三、TDD 开发流程（7阶段）

每个功能/模块按此流程：

```
1. 理解需求
   → 阅读产品规划文档中对应维度的设计
   → 确认指标、规则、参数

2. 设计
   → 确定数据结构、组件结构、3D场景结构
   → 确定测试用例（输入→预期输出）

3. 写测试（先写测试）
   → 单元测试：核心计分逻辑、难度递增逻辑
   → 组件测试：HUD显示、反馈浮层

4. 写实现
   → 按测试驱动写代码
   → 跑测试 → 失败→ 修复 → 通过

5. 验证
   → npm run lint 通过
   → npm run typecheck 通过
   → npm run test 全部通过
   → 浏览器手动验证3D场景视觉效果

6. 重构
   → 消除重复代码
   → 提取共享逻辑到 shared/
   → 跑测试确认重构无破坏

7. 提交
   → 自检代码审查清单（见开发规范.md）
   → git add（只加相关文件）
   → git commit（规范信息）
   → push → 创建PR
```

## 四、测试要求

### 测试分层

| 层 | 工具 | 覆盖范围 | 必须测试 |
|----|------|---------|---------|
| 单元测试 | Vitest | 计分逻辑、难度参数计算、数据转换 | ✅ 所有核心逻辑 |
| 组件测试 | Vitest + React Testing Library | HUD组件、反馈浮层、设置表单 | ✅ 交互组件 |
| E2E测试 | Playwright | 首页→测试→结果→注册→训练全流程 | ✅ 关键用户流程 |
| 3D视觉测试 | 手动 | 训练场景视觉、特效、灵敏度 | 手动验证 |

### 测试命名

```typescript
// 文件：src/modules/d1-reaction/__tests__/scoring.test.ts
describe('D1 反应速度计分', () => {
  it('正常反应时间应正确计分', () => { ... })
  it('反应时间超过阈值应判为miss', () => { ... })
  it('连续反应应计算平均值', () => { ... })
})
```

### 覆盖率目标

- 计分逻辑：≥ 90%
- 难度管理：≥ 80%
- UI组件：≥ 60%
- 3D场景：手动验证（覆盖率不计）

## 五、Pre-commit 钩子配置

```json
// package.json 中的 husky + lint-staged 配置
{
  "scripts": {
    "lint": "eslint . --ext .ts,.tsx,.astro",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "test:watch": "vitest",
    "e2e": "playwright test",
    "prepare": "husky install"
  },
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix", "tsc --noEmit"],
    "*.{ts,tsx,astro}": ["prettier --write"]
  }
}
```

**.husky/pre-commit 脚本：**
```bash
#!/bin/sh
. "$(dirname "$0")/_/husky.sh"
npx lint-staged
# 密钥检测
! grep -rE "(api_key|secret|token|password)\s*[:=]\s*['\"]" --include="*.ts" --include="*.tsx" src/
```

## 六、CI/CD 流程

### GitHub Actions（.github/workflows/ci.yml）

```yaml
name: CI
on: [push, pull_request]
jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run test
      - run: npm run build
```

**规则：**
- `lint` / `typecheck` / `test` / `build` 任一失败 → 阻止PR合并
- 全部通过 → Vercel 预览部署生成预览URL
- PR合并到 `main` → Vercel 生产部署

---

## 七、部署流程

```
开发完成 → push到feature分支 → PR创建 → CI自动检查
  ├─ 检查不通过 → 修复后重新push
  └─ 检查通过 → Vercel生成预览URL
      → 用户在浏览器验证
      ├─ 不满意 → 继续在feature分支修改
      └─ 确认OK → 合并到dev → 最终合并到main → 生产部署
```

**部署前必做：**
- 用户确认"可以部署"
- 检查 `.env.local` 中的密钥未提交到 git
- 检查 `npm run build` 在本地通过

**Supabase数据库变更：**
- 先在本地Supabase测试
- 通过后写migration SQL
- 用户确认后执行
- 变更SQL提交到git仓库
